| Issue | Status | Notes |
|-------|--------|-------|
| **Scene editor autosave wipes the entire scene to `{"entities": {}}` — silent project data loss on every editor visit** (found 2026-08-25, session-19 UNIT 2 acceptance check 3) | **Fixed 2026-08-25** — this commit on `fix/autosave-wipe` (code + regression tests + docs same-commit); verified: 6/6 unit regression tests + live browser check (no-edit visit leaves file intact >9s; add-entity autosave persists proper array; reload shows all entities) | Repro (fresh throwaway project seeded with 3 entities): open Scene Editor → make NO edits → within ~6s the page's autosave debounce fires and `scenes/main-scene.json` becomes `{"name":"Main Scene","entities":{},"metadata":{…}}`. Adding an entity works in editor state (hierarchy shows it) but the next autosave write still lands as `"entities": {}`, so NOTHING ever persists and reload shows an empty scene. Root cause: `SceneEditorPage.tsx` ~L73 wires `useAutosave(scene, data => api.writeFile(..., JSON.stringify(data)))` against the RAW editor scene whose `entities` is a JS **Map** — `JSON.stringify(map)` emits `{}`. The manual Save button path is correct (`serializeEditorScene()` serializes the Map to a proper array). Introduced in `5db2438` when the autosave indicator hook was wired. Real casualty observed: platformer dev project "Dancing Storm" (`OaTFxCDy9Bb`) found wiped at 2026-08-25 22:07 during the prior crashed session's editor visit (restored afterwards from canonical `templateScenes.platformer`). Fix shipped: (1) autosave saveFn calls `serializeEditorScene(data)` instead of raw `JSON.stringify`; (2) autosave armed only after first real edit via loaded-scene identity baseline (`loadedSceneBaselineRef`) — the null→loaded transition no longer triggers a pointless write-back; (3) `useAutosave` gained an `enabled` gate + null-data guard so a never-loaded scene is never saved, and project switches clear scene+baseline first (stale-scene-under-new-projectId race). Regression tests: `apps/web/src/test/autosave-wipe-regression.test.tsx`. Live verification project: `AUTOSAVE-FIX-VERIFY` (`o-uWJ1_Y-n3`). |
| **Game Preview page never mounts the Phaser runtime** (found 2026-08-23, session dead-code-batch-1) | **Fixed 2026-08-23** — commit `5953df5` on `fix/preview-mount-race`; verified: host populates, canvas renders | Repro: create project from Platformer template → Game Preview → "Loading game engine..." clears but `.game-preview-runtime-host` stays empty (0 children), no canvas, zero console errors. Start Game only sets state + focuses a canvas that does not exist. | Recipe verification pixel metric occludes on convergent chasers | Open (test-tooling limitation, not a product bug) | Found 2026-08-25, slice-2d QA (session-17). When player and enemy move toward each other they overlap on screen; pixel-diff sampling of the enemy sprite saturates once the sprites coincide, so distance deltas read null/plateau even though chase behavior is correct. Chip edit itself proven valid: runtime reads `ai.speed` at `ClawgamePhaserScene.ts:298`; numeric position sampling showed baseline contact closure 1.5→0.5 px and mutated textbook chase 142→57→contact. Recommendation: future recipe verification should sample numeric entity positions (`__probe.handle.getScene()`) instead of pixel metrics for motion recipes. Same saturation observed again in session-19 live walkthrough: red-enemy-centroid closure rate read ~0.83 px/frame both before and after the angry-enemy chip (100→170) because enemies reach contact inside the sampling window; the chip's data-level effect was verified on disk instead (`scenes/main-scene.json` `ai.speed` 100→170). |
